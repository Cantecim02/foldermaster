# Sosyal giriş mimarisi — kurulumu bekleyen plan

Bu branch'te Apple/Google/Facebook giriş endpoint’i, etkin giriş butonu, provider SDK veya OAuth secret eklenmedi. Öncelik Apple → Google → Facebook. Mevcut e-posta/şifre hesabı ve purchase appAccountToken değişmez. Dış servis yapılandırmaları doğrulanmadı; değerler uydurulmaz.

## Önerilen hesap modeli

İleride ayrı migration ile `account_identities` tablosu:

- `id`, `user_id REFERENCES users(id) ON DELETE CASCADE`, `provider`, `issuer`, doğrulanmış `subject`, `created_at`, `last_verified_at`.
- `UNIQUE(provider, issuer, subject)`; provider subject yalnız doğrulanmış tokendan alınır. `UNIQUE(user_id, provider)` ilk sürümde tek identity/provider politikasını zorlar. Bir identity başka kullanıcıya bağlanamaz.
- Email opsiyonel metadata’dır; email eşleşmesi, `email_verified` veya Apple relay email hesabı otomatik birleştirme yetkisi değildir. Account eşleştirme provider/issuer/subject üzerinden yapılır.
- Password login’siz sosyal hesap için `users.password_hash` ve email modelinin ayrı migration’ı gerekir: `password_hash` nullable; login yalnız hash varsa doğrular ve hesap keşfine yol açmayan aynı hata döner. Email yoksa sahte adres üretmeyin; nullable/ayrı verified-contact tablosu ve email-login uniqueness tasarımını kararlaştırın. Bu branch hâlâ email/password hesap modelindedir; sosyal hesabı eski zorunlu alanlara zorlamaz.
- İsim boş olabilmektedir; Apple ilk yetkilendirme sonrasında isim/email vermeyebilir. İstemcinin gönderdiği isim doğrulanmış kimlik veya yetki değildir. Sunucu bu alanları isteğe bağlı, boyut kısıtlı metadata olarak işler; username fallback vardır. Relay email gerçek email gibi otomatik eşleştirmeye kullanılmaz; relay’e mail göndermek için Apple domain/mail sender kurulumu ayrı doğrulanır.
- Username random, görünür public profil değeridir. Internal user UUID ve satın alma appAccountToken ayrı kalır. Identity bağlama veya provider değişimi Apple entitlement sahibini değiştirmez.

## Doğrulama ve oturum akışı

Önerilen endpoint isimleri tasarımdır, mevcut canlı route veya kayıtlı redirect değildir:

1. `POST /auth/social/challenge`: provider allowlist; tek kullanımlık kriptografik state/nonce üret, hashini kısa TTL (örneğin 5 dakika), akış amacı ve session/user bağlantısıyla sunucuda sakla. Token/payload boyut sınırı ve rate limit uygula. Browser OAuth’ta PKCE S256 ve tam redirect eşleştirmesi kullan. Native SDK’nın raw/hashed nonce sözleşmesiyle backend karşılaştırması testlerde eşleştirilir.
2. `POST /auth/social/:provider`: TLS üzerinden credential + challenge; server seçilmiş/provider-specific doğrulayıcı kullanır. Sabit provider JWKS URL’leri ve bounded/cacheable key refresh; tokenın `jku`/`x5u` URL’sini takip etme. Vetted JOSE/OIDC kütüphanesi ve provider algoritma allowlist kullan; `none`, yanlış alg/kid/signature/issuer/audience/nonce, expired/future-invalid tokenları reddet. Client’ın claim veya userId beyanını kimlik sayma.
3. Apple: signature/JWKS, issuer `https://appleid.apple.com`, doğru native veya Services ID audience, `exp`/`iat` ve challenge nonce; authorization code tek kullanımlık server exchange ile doğrulanmalı. Access/refresh token gerekiyorsa encrypt-at-rest ve key rotation; request/proxy hata loglarından çıkarılmalı.
4. Google: signature, Google issuer allowlist, server Web client ID audience, expiry ve seçilen SDK akışının nonce/challenge binding’i; kullanıcı anahtarı `sub`. Native SDK nonce desteği yoksa client tarafından imzalanmamış nonce alanını kontrol edilmiş gibi kabul etme; server authorization-code/PKCE akışı veya destekli nonce yöntemi seçilip replay testleriyle doğrulanmalı. [Google ID token doğrulama](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).
5. Facebook: standart opaque access token için Meta sunucusuyla app-bound token inspection ve kullanıcı kimliği/süre/izin doğrulaması gerekir; JWT gibi parse edilmez. Limited Login OIDC token için resmi SDK/token belgesine göre signature/JWKS, issuer, App ID audience, nonce ve expiry doğrulanır. Aynı endpoint’e gelen token türü explicit allowlist ile seçilir; yanlış doğrulayıcıya fallback yapılmaz. Kesin JWKS/claim sözleşmesi uygulama öncesi Meta resmi kaynaklarından yeniden doğrulanacak.
6. Challenge tüketimi ve identity lookup/create aynı transaction sınırında yapılmalı; paralel isteklerde UNIQUE constraint nihai korumadır. Yeni kullanıcı için yaş beyanı ve terms/privacy kabulü e-posta kayıtla aynı politikaya tabidir. Tam DOB istenmez. Ardından mevcut rastgele session token + hash-store + SecureStore modeli kullanılır; provider tokenı app session yerine kullanılmaz. Sosyal giriş oyun/billing bonus hakkı yaratmaz.

## Hesap bağlama, çıkış ve silme

Mevcut hesabı korumak için provider bağlama açık bir kullanıcı işlemi olmalı: aktif app session + yakın zamanda mevcut password veya bağlı provider ile yeniden doğrulama + linking-purpose challenge. Aynı email bulunduğunda yeni session vermeyin, hesabı birleştirmeyin; kullanıcı mevcut hesabına giriş yapıp açıkça bağlamalı. Provider kimliği başka hesabınsa conflict döner; transaction ve audit metadata (token/email içermeyen ID/sonuç) kullanılır. Son kullanılabilir login yöntemi kaldırılamaz.

Device logout mevcut app session’ı iptal eder; sağlayıcı hesabını silmez. Account deletion sosyal hesapta boş password alanına zorlanmaz: yakın zamanda verified provider credential ile deletion-purpose yeniden doğrulama gerekir. App sessions revoke, history/account silme ve mevcut billing orphan/purchase ilişki politikası korunur. Apple aboneliği ayrı Apple subscription ayarlarından yönetilir; hesap silme otomatik abonelik iptali diye gösterilmez.

Apple hesabı silerken server-side refresh/access token revoke akışı planlanır. [Apple TN3194](https://developer.apple.com/documentation/technotes/tn3194-handling-account-deletions-and-revoking-tokens-for-sign-in-with-apple) ve [Apple token revocation](https://developer.apple.com/documentation/signinwithapplerestapi/revoke-tokens) esas alınmalı. Network failure için minimum encrypted revoke payload içeren kısa ömürlü outbox/retry tasarlanır; UI provider revoke tamamlandı diye yanlış başarı söylemez. App verisinin silinmesi gereksiz provider metadata retention’a dönüşmemeli. Token saklanmamışsa resmi yeniden yetkilendirme/manual revoke yolunu açıkça sun; sonsuza dek account deletion engellenmesin. Apple credential revocation/account-change bildirimleri doğrulanıp yerel identity/sessions güncellenir. Google/Meta bağlantı kaldırma ve data deletion callback gereksinimleri de ayrı doğrulanır.

## Uygulama öncesi güvenlik testleri

Yanlış signature/kid/alg/issuer/audience/nonce, expired token, reuse challenge/code, iki paralel identity create, email-match saldırısı, relay/missing email/name, provider offline, code exchange timeout, credential revoke, failed deletion retry ve provider-only account deletion testleri gerekir. Callback’te state/PKCE mismatch ve redirect allowlist, log redaction, secure-store failure da kontrol edilir. Her SDK/plugin değişikliği ayrı native iPhone build gerektirir; bu görev herhangi bir build/submission başlatmaz.
